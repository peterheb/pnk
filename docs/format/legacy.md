# Legacy iWork Formats (pre-'13): Detection and Rejection

pnk supports iWork '13+ only. This document lists the concrete signals that identify
pre-'13 iWork files (Pages '08/'09, iOS `.pages-tef` bundles, old Keynote/Numbers
packages), how to detect them before parsing, and the error messages to emit.

## Why rejection must happen at detection time

Every third-party parser we reference assumes the '13+ container; none of them
gracefully handles pre-'13 content:

- keynote-parser targets "Keynote files generated by Keynote version 14.4" and assumes
  a ZIP of Snappy-compressed protobuf `.iwa` files
  (`[parser: keynote-parser@56a4d3b0] .scratch/keynote-parser/README.md`, sections
  "keynote-parser" and "Compatibility"). Its unpack loop simply decodes every entry
  whose name contains `.iwa`
  (`[parser: keynote-parser@56a4d3b0] .scratch/keynote-parser/keynote_parser/file_utils.py:220`,
  `process_file`). Grep for `index.xml`, `tef`, `legacy`, `old format` in
  `.scratch/keynote-parser/keynote_parser/` returns no matches — there is no legacy
  code path at all. A legacy file therefore fails as a broken '13 file, not as a
  clear "unsupported version" error.
- numbers-parser never checks for legacy containers; its version gate is the
  `fileFormatVersion` key in `Metadata/Properties.plist`, warning (not failing) when
  the version is outside `SUPPORTED_NUMBERS_VERSIONS`
  (`[parser: numbers-parser@32387958] .scratch/numbers-parser/src/numbers_parser/iwork.py:54-93,126-128`
  and `.scratch/numbers-parser/src/numbers_parser/constants.py:76-80`). Its only
  "legacy" string hits are proto field names inside generated code, not file-format
  handling (`[parser: numbers-parser@32387958] .scratch/numbers-parser/src/protos/TSCEArchives.proto:574-576`,
  e.g. `DATE_MODE_1900_LEGACY`). Do not confuse those with legacy documents.
- dunhamsteve/iwork is the only reference repo that actually *opens* legacy formats
  (Pages '08/'09 XML, `.pages-tef` sqlite) — useful as a detection oracle, not as a
  rendering target (`[parser: iwork@02c26ebf] .scratch/iwork/README.md`).

## Container layouts across generations

Three physically different containers exist for `.pages`-suffixed files; the same
splits apply conceptually to `.key` and `.numbers`:

| Generation | Container | Index payload |
|---|---|---|
| '08 | directory bundle | `index.xml.gz` |
| '09 | flat ZIP file | `index.xml` at ZIP root |
| iOS (pre-'13) | directory bundle (`.pages-tef`) | sqlite DB `index.db` mirroring the '13 model |
| '13+ | flat ZIP file | `Index.zip` (nested ZIP of `.iwa` files) |

The '08/'09 rows are documented in the dunhamsteve README: the XSLT
`pages08tohtml.xsl` "will process the xml from Pages'08 and Pages'09 files ... You can
apply it to the index.xml.gz in a Pages'08 file bundle (which is a directory) or the
index.xml found within a Pages'09 file (which is just a zip file)"
(`[parser: iwork@02c26ebf] .scratch/iwork/README.md`, "Pages'08 and Pages'09" section;
`.scratch/iwork/pages08tohtml.xsl` exists in the repo). The iOS row: "Before the
format change in Pages'13, the iOS version of pages introduced a `.pages-tef` bundle
format for iCloud storage. It turns out that the sqlite database within these bundles
mirror the '13 format" (`[parser: iwork@02c26ebf] .scratch/iwork/README.md`,
"iOS '.pages-tef' files" section). The '13+ row is confirmed by numbers-parser, which
requires `Index.zip` inside a package directory and reads `.iwa` blobs out of it
(`[parser: numbers-parser@32387958] .scratch/numbers-parser/src/numbers_parser/iwork.py:140-143,196-218`).

## Detection signals

Order these checks cheap-first. Any single hit means "legacy: reject".

### 1. File extension

- `*.pages-tef` — iOS Pages bundle. The `-tef` suffix is stripped programmatically in
  dunhamsteve's opener: `indexType := strings.TrimSuffix(filepath.Ext(doc)[1:], "-tef")`
  (`[parser: iwork@02c26ebf] .scratch/iwork/index/index.go:33-34`).
- `.key-tef` / `.numbers-tef` — NOT documented anywhere in the four reference repos;
  grepping `.scratch/` for `key-tef` / `numbers-tef` / `.tef` yields no hits beyond
  the Pages README and the `-tef` suffix handling above
  (`[inferred: only ".pages-tef" appears in .scratch/iwork/README.md:44-48; the
  TrimSuffix in index.go:34 is format-agnostic, so analogous iCloud bundles for the
  other apps are plausible but unverified — verify against fixtures before claiming]`).
  Treat any `*-tef` extension as legacy; do not special-case the app.

### 2. Input is a directory (bundle, not a flat file)

iWork '13 files are normally flat ZIPs; legacy '08 bundles and `.pages-tef` are
directories. litchi's path detection branches on `path.is_dir()` exactly this way
(`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:156-166`,
`detect_iwork_format_from_path`). A directory input with the markers below is legacy.

### 3. ZIP contents (flat-file input)

Inspect the ZIP entry list; no decompression needed:

- Presence of `index.xml` at the ZIP root is the definitive Pages '09 signal: the
  dunhamsteve README identifies "the index.xml found within a Pages'09 file (which is
  just a zip file)" (`[parser: iwork@02c26ebf] .scratch/iwork/README.md`). litchi also
  probes for `index.xml` inside bundles
  (`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:214-217`).
  `[inferred: "at ZIP root" is a mild extrapolation from the README wording; verify
  entry prefix in a fixture — a `index.xml` under any single top-level directory
  should be treated as suspicious too]`.
- Absence of `Index.zip` (and of any `*.iwa` entries) in a ZIP whose name claims to be
  a `.pages`/`.key`/`.numbers` file. The '13 format is "a zip file containing images
  and videos, as well as Snappy-compressed Protobuf .iwa files"
  (`[parser: keynote-parser@56a4d3b0] .scratch/keynote-parser/README.md`), and
  dunhamsteve's loader for '13+ files opens `<bundle>/Index.zip` first
  (`[parser: iwork@02c26ebf] .scratch/iwork/index/index.go:35-44`). No `Index.zip` and
  no `.iwa` entries means pre-'13.
- litchi's byte-level gate is the same test: `detect_iwork_format_from_bytes` returns
  `None` unless some entry name ends with `.iwa`
  (`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:136-145`).

### 4. Directory contents (bundle input)

- `index.xml.gz` present → Pages '08 bundle (`[parser: iwork@02c26ebf] .scratch/iwork/README.md`).
- `index.db` (sqlite) present → iOS `.pages-tef` bundle; dunhamsteve falls back to
  opening `<bundle>/index.db` and queries `objects` joined with `dataStates`
  (`[parser: iwork@02c26ebf] .scratch/iwork/index/index.go:49-58,65-67`).
- `index.apxl` present → legacy Keynote (pre-'13 packages used an XML/apxl index).
  litchi maps this to Keynote
  (`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:208-212`).
  `[inferred: the "legacy Keynote" identification is our conclusion from apxl being an
  XML index format, not from a parser comment; litchi does not label it legacy]`.
- `index.numbers` present → legacy Numbers package index; litchi probes for it
  (`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:220-224`).
  `[inferred: same caveat as apxl — treated as legacy because '13+ Numbers uses
  Index.zip + .iwa, verified in numbers-parser iwork.py:141]`.
- Absence of `Index.zip` in a directory that otherwise looks like an iWork package:
  numbers-parser treats `Index.zip` as mandatory for a Numbers package ("folder is not
  a numbers package" otherwise)
  (`[parser: numbers-parser@32387958] .scratch/numbers-parser/src/numbers_parser/iwork.py:140-143`).

### 5. Gotcha: litchi does NOT flag legacy bundles as legacy

litchi's `detect_iwork_format_from_bundle_files` returns `FileFormat::Pages` /
`Keynote` / `Numbers` for the legacy markers above with no legacy distinction — its
module docstring claims coverage of "both modern iWork '13+ formats ... and legacy
formats" but the return type carries no legacy bit
(`[parser: litchi@92293640] .scratch/litchi/crates/litchi/src/detection_smart/iwork.rs:3-4,207-224`).
If pnk reuses litchi-style detection, add the legacy checks of this document *before*
accepting its result, otherwise a Pages '09 file will be reported as a normal Pages
document and then fail during IWA parsing.

## Recommended rejection behavior

Detect-and-reject at open time, before any IWA/sqlite work. Suggested messages for
the pnk viewer `[inferred: wording is ours; the factual predicates are those cited
above]`:

- `Unsupported file: this is a legacy iWork document (Pages '08/'09 or iOS-era
  format). Re-save it with a current version of Pages, Numbers, or Keynote and try
  again.` — for `index.xml` / `index.xml.gz` / `index.apxl` / `index.numbers` markers.
- `Unsupported file: iOS iWork bundles (*.pages-tef) are not supported. Open and
  re-save the document in a current version of Pages.` — for `-tef` extensions and
  `index.db` bundles.
- `Unsupported file: no iWork '13+ data found (missing Index.zip / *.iwa entries).`
  — for a ZIP or bundle that matches none of the '13+ container invariants
  (`Index.zip` present, `.iwa` entries present; see
  [container.md](container.md) and [objects.md](objects.md) for the '13 layout).

All three should be emitted as the same error class (unsupported-version), distinct
from "corrupt file" and "unknown format", so callers can offer a re-save hint. Keep
the detection predicate list in one function so new legacy signals land in one place
`[inferred: engineering preference, no parser basis]`.
